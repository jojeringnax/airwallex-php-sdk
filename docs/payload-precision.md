# Payload precision

The [consumer interface](consumer-interfaces.md#interface-conventions) owns public payload representation. The internal JSON codec implements that representation; endpoint contracts supply the decimal and integer positions for each operation.

Consumers pass money and other schema-defined decimal fields as plain base-10 strings, such as `'19.90'`, `'0'` or `'0.000000000001'`. The codec writes exact JSON number tokens at those positions. PHP floats, integer arguments, exponent input, leading plus signs and leading zeroes are rejected for decimal fields. Subscription Update `items[*].proration_value.charge_amount` and `credit_amount` are provider-schema strings: [custom amounts](billing-resources.md#choosing-subscription-financial-controls) use the same plain decimal syntax but remain exact JSON strings. Other string fields, including numeric-looking identifiers and metadata, stay JSON strings. Negative decimal syntax is supported by the codec; each endpoint controls allowed signs, bounds, currency scale and nullability.

No amount passes through floating-point conversion. Responses retain the original numeric text at known decimal positions, including integer-valued amounts. Known integer positions become PHP integers when the token is an integer within the runtime range; oversized integers and other numeric representations remain exact strings. Every unknown numeric field also remains a string. Unknown status strings, timestamps, missing keys, explicit nulls and additional response fields retain their values. By default, nonempty objects become associative arrays; nested empty objects become `stdClass`, and JSON arrays remain arrays. The root resource object becomes an array, including an empty array for `{}`.

## Object shape and proof limits

The opt-in interface for [#156](https://github.com/jojeringnax/airwallex-php-sdk/issues/156) preserves nested objects as `stdClass`. The default remains compatible with the released array representation: PHP coerces canonical integer property names to array keys, so default decoding cannot distinguish `{"0":"zero"}` from `["zero"]`. Use object mode when that distinction contributes to read evidence.

| Surface | Selection and result |
| --- | --- |
| Resource responses | Construct `Client` with the optional final argument `preserveResponseObjects: true`. Every successful Billing and Payments response, including mutation results, lists and subordinate reads, keeps nested objects as `stdClass`. A client derived with `forConnectedAccount()` retains this setting. |
| Webhook view | `WebhookEvent::fromJson($rawBody)->toArray(preserveObjects: true)` keeps nested objects as `stdClass`. Each view is independent: changing an object in a returned view does not change the event or later views. `toArray()` and `toArray(false)` retain the default representation. Verify the original body before decoding. |
| Root and lists | Roots are known JSON objects and always return PHP arrays, including `[]` for `{}`. Every nested JSON object, populated or empty, is `stdClass` in object mode; JSON lists remain PHP lists, with their elements decoded recursively. |
| Values | Both modes apply the same endpoint/webhook integer selection and exact decimal rules. Quoted strings, unknown fields, booleans, explicit nulls and absent fields retain their existing semantics. |

For a response with `"metadata":{"0":"zero"}`, read `$customer['metadata']->{'0'}` after checking `instanceof stdClass`. A response with `"metadata":["zero"]` remains a PHP list and fails that object check. For arbitrary object keys, `get_object_vars($object)` exposes the fields, including names PHP cannot access through property syntax. Keep the `stdClass` type check before that conversion: its resulting PHP array alone no longer proves object shape. Use `property_exists($object, 'field')` to distinguish a present null from absence.

This surface preserves decoded object/list shape, not arbitrary wire provenance. Unknown numeric tokens and quoted numeric strings can produce the same PHP string; known integers follow the existing schema rules. Duplicate decoded keys, including escaped spellings of the same key, retain only their last value. Whitespace, escape spelling, duplicate occurrences and raw number-versus-string identity are not exposed as proof. Re-encoding a view does not reproduce the original bytes or necessarily the original scalar token types. Consumers retain the original raw body separately when their validation requires it; signed webhooks must always use the original bytes. Shape evidence alone establishes no ownership, provider validity, command equivalence or permission to replay a write.

**Availability:** this is the unreleased #156 addition; SDK **v0.1.1** does not provide these options. A consumer such as [Laravel #37](https://github.com/jojeringnax/airwallex-laravel/issues/37) must qualify a release or exact merged revision containing the addition and retain its Composer lock reference before depending on it. No release or Laravel qualification is recorded by this source change.

At the unchanged API/webhook baseline **2026-08-21**, the official [Billing Customer contract](https://www.airwallex.com/docs/api/billing/billing_customers) describes metadata as an object of string key/value pairs (rechecked **2026-11-11**). The [webhook guide](https://www.airwallex.com/docs/developer-tools/webhooks/listen-for-webhook-events) describes JSON payloads and verification of their original bytes (rechecked the same day; the guide is not date-versioned). Object mode is an SDK representation choice. Synthetic list-shaped metadata in decoder regressions is a negative shape example, not an observed provider response or an assertion that the provider permits lists there. Authentication, account context and endpoint schemas are unchanged.

## Numeric and validation boundaries

For selected-version webhook envelopes, the [catalogue guards](webhook-contracts.md#php-verification-and-decoding) select known integers in generic `data.object` resources and direct `billing_checkout.*`, `subscription.*` and `invoice.*` resources without an `object` key. Subscription selection reuses exactly `days_until_due`, `duration.period`, `recurring.period` and `applied_discounts[*].duration.period`; Invoice reuses `days_until_due`, `past_payment_attempt_count`, `remaining_payment_attempt_count` and `applied_discounts[*].duration.period`. A numeric zero duration in a matching CANCELLED snapshot is therefore PHP `int` zero; quoted zero, decimal/exponent forms, overflow and unknown numbers stay strings. Integer representation does not validate a field's sign, minimum, requiredness or business meaning, and changes no request schema. Development consumers should update string-only expectations at these direct Subscription and Invoice positions; the [consumer migration example](consumer-examples.md#webhook-boundary) preserves raw shape and application-owned acceptance.

The codec performs no arithmetic, rounding, scale truncation, currency conversion or proration. Endpoint validation owns provider-supported currency/scale constraints; there is no SDK currency whitelist. An operation must have its schema verified before it can promise amount and null semantics. The [API baseline](api-contracts.md#version-baseline) is `2026-08-21`; the provider [data types](https://www.airwallex.com/docs/api/data_types) describe amounts in major units. For example, selected-version [Price creation](https://www.airwallex.com/docs/api/billing/prices/create) defines `flat_amount`, `unit_amount` and tier amounts as numbers, whereas recurring period and lot size are integers. [Payment Intent creation](https://www.airwallex.com/docs/api/payments/payment_intents/create) defines a numeric amount and points to provider currency minor units. Sources were inspected on 2026-11-08; this codec contribution does not claim endpoint or sandbox validation.

The codec rejects malformed JSON, non-object resource roots and nesting beyond 128 levels with `ProtocolException`; invalid request values raise `ValidationException`. Diagnostics use fixed descriptions and omit payload values. Unit cases cover exact wire bytes, fractional and integer-valued amounts, very large values, high-precision prices, null/absence/empty shapes, unknown fields, integer overflow and malformed responses. These cases establish serialization behavior, while endpoint fixtures and opt-in sandbox journeys establish provider compatibility.
