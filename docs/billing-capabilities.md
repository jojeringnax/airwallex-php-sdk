# Billing capability boundaries

Contract review for [issue #5](https://github.com/jojeringnax/airwallex-php-sdk/issues/5), verified on **2026-11-08** against API **`2026-08-21`**. This reference defines document access, checkout, self-service and trial boundaries for later interfaces. [Planning](planning.md) owns release scope; the [API inventory](api-contracts.md) owns version policy and the [connected-account reference](connected-account-contracts.md) owns authorization and linkage.

## Accepted scope

| Capability | Initial SDK scope | Consumer responsibility / boundary |
| --- | --- | --- |
| Invoice documents | Return provider `pdf_url` and `hosted_url` through invoice retrieval | Authorize the buyer, download or redirect, store and deliver documents; no SDK PDF renderer, downloader or mailer |
| Checkout | Server-side create/retrieve/update/cancel for `HOSTED`, `EMBEDDED` and `ELEMENTS`, across supported `PAYMENT`, `SUBSCRIPTION` and `SETUP` modes | Redirect or integrate Airwallex.js; browser components remain outside the PHP package |
| Self-service | Verified customer, source, subscription and invoice API operations underpin an application portal | Application owns UI, tenant authorization, persistence and reconciliation; provider-hosted Billing portal sessions deferred pending a verified contract |
| Provider trials / future starts | Subscription `starts_at` and `trial_ends_at`, including checkout `subscription_data` | Application chooses dates and access policy; provider owns remote trial and billing state |
| Generic local trials | Outside SDK implementation | Application stores trial dates and grants access, creating remote Billing resources when its policy requires |
| Cancellation | Immediate cancellation and documented scheduled-ending fields | Application owns grace/access policy; schedule-restoration claims stay within the scoped evidence below; cancelled-subscription reactivation and pause APIs deferred |

These boundaries retain native provider capabilities without adding application infrastructure to the framework-independent package. Link exposure avoids coupling the SDK to document storage/delivery. Supporting checkout UI modes at the server boundary lets applications choose their browser experience while sharing one Billing contract.

## Selected-version evidence

The official [Invoices API](https://www.airwallex.com/docs/api/billing/invoices), [Billing Checkouts API](https://www.airwallex.com/docs/api/billing/billing_checkouts) and [Subscriptions API](https://www.airwallex.com/docs/api/billing/subscriptions) page metadata each reported `currentVersion=2026-08-21`. Request properties, resource schemas and endpoint lists were inspected in `activeCategory`. All endpoints in these three groups report organization resource level and no on-behalf-of support. Use credentials authorized for the owning Billing organization, not a Payments delegation header. Linked collection-account eligibility still follows the connected-account reference.

### Invoice access and delivery

`GET /api/v1/billing/invoices/{id}` returns the Invoice schema. Its `pdf_url` is a download link valid for 35 days and is `null` before finalization. `hosted_url` lets a customer view/pay an invoice and is also documented as valid for 35 days. The schema does not establish the clock origin or guarantee that every retrieve regenerates either link. The [invoicing guide](https://www.airwallex.com/docs/billing/invoicing/get-started-with-invoicing) describes digital links as valid for 35 days after the due date and obtaining a new link via the web app or API. Preserve this validity-clock ambiguity for expiry/refresh validation rather than calculating an SDK expiry or promising renewal on every read.

The [Billing setup guide](https://www.airwallex.com/docs/billing/get-started-with-billing) describes provider invoice email delivery to the supplied customer email address. That is provider behavior, not an SDK send/resend API contract. No dedicated PDF generation, binary download or email-send operation was found in the inspected 17 Invoice endpoints. This limits the verified SDK contract; it does not prove such provider features never exist.

Consumer scenario: authorize the local buyer against the stored Billing Customer mapping, retrieve their invoice under the owning organization and return the available PDF/view link. A draft's null PDF is an expected state. If a link is expired, retrieve current resource data; confirm refresh behavior in sandbox or with Airwallex before promising a replacement. Downloading, archiving and emailing belong to the application. A separate [owned paid-Invoice prefix observation](https://github.com/jojeringnax/airwallex-php-sdk/issues/42#issuecomment-6747496167) followed one admitted 301 redirect and received 200 with a `%PDF-` prefix; full PDF validation, link lifetime/expiry and refresh behavior remain unverified.

### Checkout UI contracts

Create uses `POST /api/v1/billing/billing_checkouts/create`; `ui_mode` accepts `HOSTED` (default), `EMBEDDED` or `ELEMENTS`. The Checkout response includes `client_secret` only for the two embedded modes. Its `url` is present only while `ACTIVE`; the selected status schema describes unpaid checkouts expiring after one hour. The [embedded guide](https://www.airwallex.com/docs/billing/billing-components/checkout/embedded-billing-checkout) and [Elements guide](https://www.airwallex.com/docs/billing/billing-components/checkout/billing-checkout-elements) describe browser initialization using that secret. These use Billing Checkout, whereas Payments Elements operate on Payment Intents; the [comparison](https://www.airwallex.com/docs/billing/billing-components/checkout) distinguishes them.

A [sandbox observation](https://github.com/jojeringnax/airwallex-php-sdk/issues/42#issuecomment-6722652823) at API `2026-08-21` instead returned `expires_at` exactly 2,592,000 seconds after `created_at` for all nine mode/UI combinations. Their owner, entity, collector, currency, metadata, UI and applicable item fields matched; create/retrieve/metadata-update/cancel controls passed for each. The financial modes used explicit `invoice_data` or `subscription_data`. No actual expiry transition or Checkout completion was observed in those historical controls; the timestamps do not establish a 30-day lifetime or resolve which clock governs status. A later [ordinary HOSTED SETUP](https://github.com/jojeringnax/airwallex-php-sdk/issues/42#issuecomment-6746998357) completed and reconciled its owned Source/Method/Consent mapping; Separate [Hosted PAYMENT and SUBSCRIPTION cases](sandbox-validation.md#ordinary-hosted-saved-card-and-billing-collection) now establish owned completion and initial paid-Invoice reads, with Subscription cancellation and catalogue cleanup. Later renewal, natural ending and signed completed-Checkout delivery remain unverified. Expose the returned values and retrieve current status rather than calculating a guaranteed TTL. Airwallex clarification of this discrepancy remains under #42.

Consumer scenario: create an on-demand `SUBSCRIPTION` checkout with a recurring price, owning legal entity, eligible collection account and request ID. For `HOSTED`, redirect to `url`; for `EMBEDDED` or `ELEMENTS`, pass only the checkout client secret and necessary configuration to the authorized browser and mount the appropriate Airwallex.js component. Keep API credentials and bearer tokens server-side and redact client secrets from diagnostics. Retrieve the checkout and resulting resources or process verified webhooks to reconcile completion; a browser success callback/redirect alone establishes neither settlement nor application entitlement. Mode-specific examples and PHP method conventions are defined in [interface examples](consumer-examples.md#customer-linkage-and-checkout); server operations and deterministic fixtures were implemented under [#21](https://github.com/jojeringnax/airwallex-php-sdk/issues/21), while actual completion and provider evidence remain under #42.

### Self-service and portal evidence

The [sample integration](https://www.airwallex.com/docs/billing/subscriptions/subscriptions-via-api/sample-integration) discusses a customer portal and backend synchronization. It does not specify a hosted Billing portal-session endpoint, authentication, return URL or permitted-action contract. The reviewed Billing resource endpoints do not establish one either. The [Airi portal](https://www.airwallex.com/docs/payments/payment-methods/global/airi) manages shoppers' saved payment details; it is not evidence for Billing subscription self-service sessions.

Consumer scenario: the application's authenticated portal retrieves the buyer's invoices, requests supported plan/quantity changes, or schedules cancellation through organization-authorized backend calls. To replace an instrument, collect it using an approved setup flow, verify ownership, then update the subscription source. The Subscription update schema documents an immediate retry of the last failed invoice payment when `payment_source_id` is updated. A [scoped Sandbox recovery](https://github.com/jojeringnax/airwallex-php-sdk/issues/28#issuecomment-6747983907) now observed one owned UNPAID Subscription and the same unpaid Invoice become ACTIVE and PAID/due zero after one explicit Source update. Account-configured retry cadence, exhaustion and final-action outcomes remain unverified; zero remaining attempts after payment is not exhaustion. Source changes therefore require an explicit consumer action and financial-side-effect documentation; see [#28](https://github.com/jojeringnax/airwallex-php-sdk/issues/28). Source deletion/default-management and a hosted portal API remain unverified, not inferred from UI mentions.

### Trials, cancellation and grace

Subscription create accepts `starts_at` (immediate by default) and `trial_ends_at`; Checkout create accepts both within `subscription_data`. The [subscription guide](https://www.airwallex.com/docs/billing/subscriptions/subscriptions-via-api) places the trial start at `starts_at` and excludes the trial from billing duration. Its update table permits start changes in `PENDING` and trial-end changes in `PENDING`/`IN_TRIAL`. The update schema documents `NOW` for immediate pending start or trial termination. Preserve timezone and precision; full range/error fixtures belong to [#23](https://github.com/jojeringnax/airwallex-php-sdk/issues/23).

Consumer scenario: choose a future `starts_at` and later `trial_ends_at`, create the remote subscription (or a subscription checkout), then retrieve observed `PENDING`, `IN_TRIAL` and subsequent billing state. A local trial instead exists solely in application storage until remote creation; it does not imply an Airwallex subscription or suppress provider billing. PHP representations are defined in [interface examples](consumer-examples.md#saved-instrument-and-direct-subscription).

Immediate cancellation uses `POST /api/v1/billing/subscriptions/{id}/cancel` with required `request_id` and `proration_behavior`: `ALL` refunds the current-period charge, `PRORATED` refunds the prorated amount, and `NONE` refunds no unused time. The product guide says cancellation is permanent and stops pending automatic subscription payments. It is not a promise that outstanding invoices are voided.

Scheduled ending uses Subscription update: `cancel_at_period_end=true` schedules period-end cancellation; `ends_at` supplies a scheduled end, while creation allows it only when `duration` is empty. Update also exposes `duration`/`remaining_duration`; their interaction and schedule-clearing behavior require fixtures before convenience methods are defined. `cancel_at_period_end=false` exists in the schema, but the product update table omits this field and provides no complete reversal rules. Include the documented field in the resource contract; limit reversal claims to the applicable non-cancelled-state evidence below. Never describe it as reactivation of a cancelled subscription. No pause/resume endpoint or paused state was found among the seven inspected Subscription endpoints and status enum.

Consumer scenario: retrieve the subscription, request period-end ending, and reconcile the returned schedule. The application may retain access through its chosen paid-through date. For a finite schedule, save the exact original future `ends_at` and separate schedule/restoration request IDs durably before setting true. If a supported buyer action later restores that finite end, send false with the saved end and verify the owned state; never infer the old cap from the shortened post-scheduling response. The [executed consumer recipes](consumer-examples.md#changes-cancellation-and-invoice-access) preserve this ordering. After permanent cancellation, any new subscription is a separate financial resource. Access grace never delays a provider cancellation or charge by itself.

A [fresh Sandbox control](https://github.com/jojeringnax/airwallex-php-sdk/issues/42#issuecomment-6723780660), source `f87800bfd7a41ca0824044b4ba70bc0feb855904`, API `2026-08-21`, verified this explicit restoration on an organization-owned ACTIVE EUR OUT_OF_BAND Subscription with a daily Price and seven-day lifetime. Before scheduling, its finite end exceeded the first daily period. True shortened the visible end to the current period and changed the visible duration. A separate update with `cancel_at_period_end=false` plus the exact saved original `ends_at`, omitting duration/remaining_duration, was retrieved as ACTIVE/false with the original end and duration restored. Own cancellation and catalogue archives passed; no instrument or automatic collection was used. This supports that finite-state request, not false-alone reversal, other states/collection methods, every field interaction or indefinite renewal. Earlier false-alone controls remained pending within bounded reads. A separate ACTIVE remaining-duration-only update was accepted with finite readback but its precise timing remains unverified. Provider financial effects, trial completion and broader evidence remain under [#42](https://github.com/jojeringnax/airwallex-php-sdk/issues/42).

For recovery, the [API inventory](api-contracts.md#payment-recovery-conflict) records the fixed-retry API introduction versus configurable [dunning guide](https://www.airwallex.com/docs/billing/subscriptions/dunning). Preserve observed `UNPAID`/`ACTIVE`/`CANCELLED` state and account settings; no universal retry schedule, inevitable cancellation, SDK collection scheduler or automatic access cutoff follows from this review.

### Adoption timing and restoration contracts

The [subscription ownership decision](planning.md#initial-billing-and-payments-scope) keeps the SDK's subscription operations stateless. The caller supplies the intended finite end or indefinite-continuation request; the SDK stores no original schedule and runs no future job. Persistence, application access dates and coordination of competing changes belong to the consumer. A pending-cancellation reversal continues the same Subscription; permanent cancellation remains terminal. The orchestration requirements below describe consumer responsibilities, not additional SDK services.

[Research #158](https://github.com/jojeringnax/airwallex-php-sdk/issues/158) rechecked the official [Subscription API](https://www.airwallex.com/docs/api/billing/subscriptions), [API guide](https://www.airwallex.com/docs/billing/subscriptions/subscriptions-via-api) and [management guide](https://www.airwallex.com/docs/billing/subscriptions/get-started-with-subscription-management) on **2026-11-11** for [the downstream consumer contract](https://github.com/jojeringnax/airwallex-laravel/issues/47). The page selected `currentVersion=2026-08-21`, specification `airwallex-openapi-2026-08-21.yaml`, advertised MD5 `6caa23f3759634e64859ff6aa8c37336`. Update's `starts_at`, `trial_ends_at`, `duration`, `remaining_duration`, `ends_at`, `cancel_at_period_end`, `billing_action`, `default_proration_mode` and `payment_source_id` schemas match the released snapshot, including descriptions. The create `duration`/`ends_at` descriptions now explicitly explain indefinite continuation and mutual exclusion; the released SDK already supports that representation. This targeted comparison establishes neither whole-schema equality nor provider/account execution. API date remains unchanged.

| Required scenario | Documented support and adoption strategy |
| --- | --- |
| Future initial start / initial free period | Native create `starts_at` and `trial_ends_at`; PENDING start can be edited and PENDING/IN_TRIAL trial end can be extended. Persist resolved commercial dates and the original action. Only canonical state establishes the provider transition; the application dates its own access. |
| Immediate upgrade | ACTIVE item update with explicit proration and billing action. Existing item price cannot be changed: delete that item and add the new `price_id`. Immediate billing can generate an invoice/collection attempt; lifecycle ACTIVE alone proves no cash payment. |
| Next-cycle downgrade | Native `default_proration_mode=NONE` documents no unused-time credit and new fees from next cycle. The API guide further describes changes taking effect next cycle; the schema does not expose separate current/future effective item sets. Application access must retain its confirmed old entitlement until its own boundary and must not treat the immediate item projection as a new entitlement or payment proof. Qualify required invoicing/item timing independently. |
| Arbitrary future price/tier phases or a downgrade after an earned free period | No phase list, future-effective item timestamp or schedule resource was found among the seven inspected Subscription operations. Use a durable application/package due transition with one exact intended update, or keep exact provider-boundary parity unavailable. `DEFER_CHARGE_AND_KEEP_CYCLE` delays proration invoicing; it is not a general future execution timestamp. |
| Extend an existing earned/free period | IN_TRIAL can extend trial end. ACTIVE cannot change trial duration under the product guide. Local free access does not suppress provider invoices. A commercially required ACTIVE billing holiday therefore needs an independently verified billing strategy; do not disguise it as an ACTIVE trial extension or an invented coupon. |
| Auto-renew off | Persist original bound intent, exact observed bounds/cycle, source/collector and separate schedule/restoration action identities before requesting period-end cancellation. Observe the resulting finite schedule cap; preserve the reservation through ambiguity. |
| Auto-renew on | Update the same Subscription with false and the intended bounds. The original finite ACTIVE OUT_OF_BAND observation above and the [2026-11-12 AUTO_CHARGE observations](sandbox-validation.md#subscription-restoration-and-next-cycle-price-observations) establish separate scoped evidence. False alone left the flag true in the fresh ACTIVE control; false plus explicit null `duration`, `remaining_duration` and `ends_at` returned the flag false and the original absence of end-limit fields. Omitted optional fields do not independently prove an unlimited future lifetime. Consumer helpers must account for their own supported combinations and positive restoration evidence. |
| Already CANCELLED / UNPAID / unknown state | CANCELLED reactivation is expressly unsupported and the fresh cancelled control returned `invalid_status_for_operation`. The update guide names only PENDING, IN_TRIAL and ACTIVE; the [scoped UNPAID observation](sandbox-validation.md#subscription-restoration-and-next-cycle-price-observations) nevertheless accepted pending-cancellation reversal while retaining UNPAID and the outstanding Invoice. Renewal restoration is separate from payment recovery. Preserve unknown states and reconcile; a replacement subscription remains a separate financial action. |

For the documented next-cycle billing request, the SDK already accepts:

```php
$changed = $client->billing()->subscriptions()->update($subscriptionId, [
    'request_id' => $persistedActionId,
    'items' => [
        ['id' => $oldItemId, 'deleted' => true],
        ['price_id' => $nextPriceId, 'quantity' => 1],
    ],
    'default_proration_mode' => 'NONE',
    'billing_action' => 'DEFER_CHARGE_AND_KEEP_CYCLE',
]);
```

Authorize and canonically preflight the same customer, subscription generation, context, supported state and complete item set first. The returned item update does not establish a completed charge, a future entitlement or exclusive effective-state proof. For deferred execution, store the due date, expected generation/cycle/items, lateness policy and stable command before dispatch; recheck them before submitting once. Worker delay can cross a renewal boundary. A mismatch or disallowed lateness holds the transition for an explicit decision instead of silently applying another period's billing semantics. An ambiguous write holds the same command and permits read recovery only. Concurrent source changes may immediately retry a failed invoice and require a separate explicit financial action. Previously created invoices are not changed by ordinary subscription edits.

The low-level indefinite-restoration request contains `cancel_at_period_end=false`, `duration=null`, `remaining_duration=null`, `ends_at=null` together. Update documents clearing and indefinite continuation for that exact null triplet, while omission leaves fields unchanged. A finite restoration instead supplies its intended original end. The SDK sends the caller's selected request without remembering earlier values. Consumers preserve original intent and reconcile the resulting state before changing their scheduled access caps. The existing finite restoration recipe remains deliberately narrow; the newer account observations do not expand that recipe's guards automatically.

[Question #161](https://github.com/jojeringnax/airwallex-php-sdk/issues/161) records the broader adoption questions. The [2026-11-12 observations](sandbox-validation.md#subscription-restoration-and-next-cycle-price-observations) add scoped AUTO_CHARGE restoration and next-cycle Invoice evidence. Other state/payment-method combinations, long-term recurrence and exact renewal races retain their own evidence limits. No native phase resource was found among the inspected operations; future orchestration remains consumer work. Account observations inform consumer qualification without making a scheduler or a database an SDK requirement.

## Delivery and evidence gates

This reference records contract boundaries and bounded observations. Executable Billing resource interfaces and deterministic examples are documented in [Billing resources](billing-resources.md). The [documentation-based completion rule](release-policy.md#documentation-based-completion) applies to every first-release issue. Account-specific Sandbox journeys, product entitlements and provider confirmation are supplemental evidence; missing, blocked or failed observations do not block SDK completion. They still limit claims about observed provider behavior and account availability.

Both connected-account Billing models remain in SDK scope under the [independent authorization and eligibility boundaries](connected-account-contracts.md). Missing provider entitlements do not remove those documented code paths or block their SDK completion. A token exchange or passing fixture does not prove an account is eligible.

An observed integration pass requires explicitly configured Sandbox credentials, sanitized diagnostics and the owning journey's identity, state and cleanup proofs. Existing failed or pending results and reconciliation obligations remain unchanged; live financial operations remain outside validation scope.

Hosted Billing portal sessions and pause/reactivation remain deliberate deferrals. Reopening them requires provider contracts, account eligibility and a separate scope decision. Application portal, document delivery, local trial and entitlement implementations remain outside this repository.
