# Sandbox validation

The integration harness is opt-in and separate from deterministic unit tests. It loads an external credential file as literal data, selects `Environment::Sandbox`, enables TLS verification, disables redirects and rejects every request outside `https://api.sandbox.airwallex.com/api/v1/`. The SDK itself never reads environment files. Guzzle is a development-only concrete PSR-18/PSR-17 implementation for this harness; consumers choose their own implementation.

Install development dependencies, then run the authentication/token-reuse scenario with an explicit context:

```sh
composer test:sandbox -- --environment=sandbox --credentials-file=/absolute/private/path/.env --scenario=authentication --context=organization
composer test:sandbox -- --environment=sandbox --credentials-file=/absolute/private/path/.env --scenario=authentication --context=account
```

The credential source must be an absolute regular local file, limited to 64 KiB; URL and stream-wrapper sources are rejected. The external file uses `AIRWALLEX_CLIENT_ID` and `AIRWALLEX_SANDBOX_API_KEY_MASTER`. Account context additionally uses `AIRWALLEX_ACCOUNT_ID` as login `x-login-as`; organization context omits that header. A successful organization login does not establish Billing permissions, and account login does not establish connected-account delegation or collection eligibility. Supply credentials independently suitable for the selected context. `AIRWALLEX_ORGANIZATION_ID` is not substituted into an undocumented login header.

The parser accepts uppercase `NAME=value` entries, optional `export`, blank lines, comments and single/double quoted literal values. It never executes shell code, expands variables or interprets escapes; malformed or duplicate names fail. Running without options reports a skip. Partial configuration, a missing file or a non-sandbox environment fails before requests. No credentials, raw responses, tokens, customer data or stack traces are printed. The result is a sanitized scenario/version/context/status envelope; authentication validates the returned expiration through the SDK and confirms a second token request reuses memory.

Authentication creates no financial resources and requires no cleanup. Later journey scenarios must identify their own resources with a unique test-run marker, retain created identifiers only in private run state, and restrict teardown to those identifiers. Where a provider offers no deletion or archival operation, report retained test resources and their lifecycle explicitly. Never sweep existing account resources or use live financial operations for validation.

## Journey prerequisites and evidence

[API contracts](api-contracts.md) and [connected-account contracts](connected-account-contracts.md#evidence-still-needed) own product permissions and eligibility. Initial Billing journeys require organization Billing activation, legal entities, catalogue configuration and independently eligible linked collection accounts. Connected merchant Billing additionally requires provider confirmation of merchant organization/credential mapping, platform access and eligible collection linkage. An account ID or successful token exchange does not establish those facts.

[Webhook contracts](webhook-contracts.md#remaining-integration-evidence) identify matching-version provider-delivery and Retrieve evidence still required for Billing envelope ownership, event availability and subscription setup. Schema-derived fixtures remain synthetic. Payment simulations require the method-specific sandbox facilities and independently verified direct/delegated account authorization.

[#17](https://github.com/jojeringnax/airwallex-php-sdk/issues/17) owns this harness and initial context checks. [#42](https://github.com/jojeringnax/airwallex-php-sdk/issues/42) owns the full accepted journey matrix: checkout/setup, subscription changes/trials/cancellation/recovery, invoice access, instruments, one-time/subsequent Payments, authorization/capture/cancel, refunds, webhook deliveries and two-account isolation. Each run must record exact commit, API/webhook version, scenario and pass/fail/blocked result without credentials or customer data. Authentication evidence alone does not satisfy those journeys or the [release gates](release-policy.md#observable-release-gates).

Official references: [sandbox environment](https://www.airwallex.com/docs/developer-tools/sandbox-environment/overview), [authentication](https://www.airwallex.com/docs/api/authentication/api_access_token), [Guzzle request options](https://docs.guzzlephp.org/en/stable/request-options.html). Contract baseline: API `2026-08-21`.

## Read-only webhook configuration observation

```sh
php tools/webhook-config-observation.php --environment=sandbox --credentials-file=/absolute/private/path/.env --state-dir=/absolute/private/run-state-directory
```

This development-only command uses an explicit account login and makes exactly one bare `GET /api/v1/webhooks` at `https://api.sandbox.airwallex.com`, pinned to `2026-08-21`. Authentication is its separate ordinary login exchange. It accepts no URL, registration ID, context, SDK-root or pagination override. There is no receiver request, registration create/update/delete, secret rotation, test delivery or re-trigger. Before authentication it durably records the read intent and source/context/tool hashes in new private run state outside every Git checkout. The local ledger identity is never added as an undocumented request field.

The default transport explicitly uses Guzzle's streaming handler with TLS verification, cookies/redirects/retries disabled, a five-second per-read timeout and a ten-second elapsed body-read deadline. Both login and configuration responses are limited to 64 KiB, including errors. Missing HTTPS stream-wrapper support fails before authentication. Zero-progress, slow positive-progress, oversize and close failures stop the observation. Injected HTTP clients are deterministic fixtures or must already provide streaming responses; this wrapper cannot undo another client's prebuffering. No runtime SDK interface or dependency is added.

Only the first page's `id`, `secret`, `url`, `events` and subscription `version` are retained, with provenance, in a separate `webhook-config.json` inside the newly created private run folder (directory mode `0700`, file mode `0600`). These values never enter ordinary ledger observations or stdout; the ledger stores only the snapshot hash. The snapshot is finalized without replacing an existing file, and both file and parent directory must synchronize before retention is reported. A failure can leave an unconfirmed private temporary or finalized file: a failed result does not certify that file's durability or authorize a follow-up. Keep this sensitive snapshot outside version control, support tickets and diagnostic output. No raw response, cursor, headers, unknown fields or delivery payload is retained.

Stdout contains fixed counts and categories: returned registrations, nonempty signing secrets, exact selected-version matches, syntactically valid HTTPS/other URLs, registrations containing known accepted Billing/Payments event names, unknown-event count and cursor states. Unknown names/versions are preserved only in the private subset. `pagination_complete` requires explicit null cursors in both directions; omitted, invalid, empty or nonempty cursors leave completeness uncertain and never trigger another page. A bounded successful read is a configuration observation only. An empty page, matching version/event or HTTPS destination cannot prove global absence, intended receiver ownership, matching run events, enablement or successful delivery. `ApiWebhook` has no owner fields. A 403 or another status does not diagnose product/account availability.

Source: selected [Webhooks API](https://www.airwallex.com/docs/api/webhooks/webhooks), version `2026-08-21`, rechecked 2026-11-08. List/Retrieve metadata specifies account level, API-key authentication, `webhook:read` and no OBO; optional list parameters are `page_size` (default 20) and opaque `page`. The introduction's organization wording does not establish an organization-wide Billing manager route. The separate [OAuth partner subscription guide](https://www.airwallex.com/docs/developer-tools/partner-connections/notifications-and-workflow-automation) uses application credentials and connect semantics; those are outside this API-key probe and the accepted SDK cut.

The selected management category exposes configuration operations, not an inspected delivery-log/raw-header API. The [Events guide](https://www.airwallex.com/docs/developer-tools/webhooks/view-and-re-trigger-webhook-events) documents web-app payload/status details with 30-day retention; it does not promise a byte-preserving export with original signing headers. Existing controlled receiver logs could supply the remaining evidence without a new receiver. Actual verification still needs that delivery's exact raw body, timestamp/signature headers and matching secret/version, plus same-family ownership retrieval. Generated signatures and configuration reads do not supply network delivery. Archived MAC correctness and original freshness are separate observations; see [webhook evidence requirements](webhook-contracts.md#remaining-integration-evidence).

A [fresh actual account-context observation](https://github.com/jojeringnax/airwallex-php-sdk/issues/42#issuecomment-6724895222), committed source `b8611ee353f2b1eaf3be3a645850a8a4eeaa0787`, passed one account login and one bare configuration GET. ## Temporary signed webhook delivery probe

This development-only experiment creates one temporary account-context registration for `payment_intent.created` and `payment_intent.cancelled`, then creates and cancels one own, unconfirmed guest Intent for `1.23 HKD`. It never confirms a payment, collects funds, creates an instrument or dispatches financial actions from a callback. Its actual result below is limited to matching captured Payments deliveries in the tested account.

The provisional service choice is recorded in open decision review [#91](https://github.com/jojeringnax/airwallex-php-sdk/issues/91). A short-lived [Cloudflare Quick Tunnel](https://developers.cloudflare.com/tunnel/get-started/quick-tunnels/) forwards HTTPS traffic to a receiver bound only to `127.0.0.1`, on a new random 256-bit path. Cloudflare terminates TLS and can process webhook payloads, including any resource `client_secret`, and signing headers. Its [HTTP data-processing description](https://developers.cloudflare.com/data-localization/regional-services/http-requests/) does not establish a Quick Tunnel zero-retention or regional guarantee. The generated triggers are synthetic, but the account-wide event subscription can also carry unrelated concurrent events of those types. Private local filtering cannot prevent that transit. No Cloudflare account or domain is provisioned; tunnel configuration is limited to this run's private empty file. The experiment does create one temporary Airwallex account registration. It uses no request-bin service, public delivery log or production API target.

```sh
php tools/webhook-delivery-probe.php \
  --environment=sandbox \
  --credentials-file=/absolute/private/path/.env \
  --state-dir=/absolute/private/run-state-directory \
  --node-bin=/absolute/path/to/node \
  --cloudflared-bin=/absolute/private/runtime/cloudflared \
  --create-one-webhook-and-intent
```

The command accepts no caller URL, old resource/action ID, alternate context or SDK-root option. Credentials and state must be outside Git; the state directory must already exist with mode `0700`. It uses explicit account login, TLS verification and API/webhook version `2026-08-21`, with no OBO. API credentials and the returned signing secret are not passed to Node or the tunnel. The secret is retained in the private snapshot; same-UID processes are not OS isolated. Node receives only the private receiver configuration; the tunnel child gets a minimal `PATH`/`LANG`/private `TMPDIR` environment and an explicit empty configuration. It does not inherit API/proxy/certificate environment variables. This is not an OS filesystem sandbox: the pinned CLI can inspect default certificate-path metadata during initialization. The Quick Tunnel startup path does not load named-account credentials.

The optional Node tools use standard libraries and add no package/runtime SDK dependency. The tunnel executable is pinned to the separately verified macOS arm64 `cloudflared 2026.10.7` binary SHA-256 `2136431d5eb467bf447d2ee514b713e192719b143aec1d9e09bf7dc290d5bb12`. Its official archive SHA-256 is `3586ccf397e98e5f437e60e7c307ca6ac463e110580503af8bb8e6f9ebf831bd`; these identify different subjects. Preparation checks verified the [tagged release](https://github.com/cloudflare/cloudflared/releases/tag/2026.10.7), GitHub asset digest and macOS Apple/Cloudflare signature requirement, then version/help parsing. GitHub attestations were unavailable; no attestation success is claimed. The harness rechecks executable bytes before launch. It performs no runtime download, update or installation. A changed runtime requires a new source-reviewed pin.

Before authentication or mutations, new durable state binds source/context/tool hashes and operation identities. Exact submitted registration/Intent/cancellation bytes are separately hashed before send. The ledger's `body_hash` binds a local operation intent, which can include target references; it must not be mistaken for an exact wire-body hash. Delete uses a local durable identity with an empty wire-body hash and adds no undocumented request field. Each mutation is sent at most once. After registration creation, its complete returned configuration and secret must be durably retained in a separate private snapshot and verified by GET before any Intent trigger. The default transport forces streaming, bounds login/error/resource bodies to 64 KiB, enforces per-read and elapsed deadlines, and follows no redirects or retries. Injected clients are fixtures or must already stream responses.

The receiver rejects ambiguous framing, duplicate signing headers, nonidentity content encoding and bodies over 64 KiB. It retains original entity bytes, the single original timestamp/signature strings, receipt clock and hashes in exclusive `0600` files inside a `0700` run folder. An empty HTTP 200 acknowledges durable quarantine only; signature verification and JSON interpretation happen afterward in PHP. Raw bodies never enter the ordinary ledger or stdout. HMAC and receipt-time freshness are checked before lossless parsing, with later freshness reported separately. The local proof is limited to 64 KiB and JSON depth 64; deeper payloads remain unrecognized, not provider-invalid. It then rejects duplicate or escaped-alias JSON object keys before event interpretation; raw captures are unchanged. This local policy does not change the SDK codec's last-wins duplicate handling. A separate private native view supplies literal envelope ID/owner types; unknown numeric values never become string-typed ownership evidence through lossless conversion, and no rounded native value enters money/resource comparisons. A nonempty legacy `accountId` also stays unrecognized, even when it equals the configured account, matching the SDK owner-recognition boundary. Unknown names, versions, owners, conflicting event identities and invalid payloads stay private and cannot satisfy known-event evidence. Duplicate and out-of-order handling remain application responsibilities; this harness performs no callback-driven mutations.

Budgets are five minutes per supervised run, 16 KiB request headers, 16 captures, 2 MiB capture storage, two active requests and 1 MiB private tunnel logs. Request/read/persistence/process deadlines and fixed failure results bound slow or failed work. Info logs remain private and bounded; debug, raw errors, URLs, signing values, provider IDs and bodies are never forwarded to operator stdout/stderr. The generated destination travels only over private child stdout IPC, which PHP consumes without relaying. Node's independent deadline/EOF handling stops its owned receiver and tunnel even if the PHP controller stops responding.

Normal teardown first re-verifies and journals deletion of only the exact durable own registration, requires `deleted=true` and a subsequent GET 404, then stops and reaps the owned processes. A failed/ambiguous registration create or undurable returned ID/secret blocks Intent triggers, recreation and guessed deletion; its original intent/provenance remains reconciliation work even after process shutdown. A failed/unfinished Intent action blocks dependent mutations. Separately proven registration cleanup uses a fresh journal so it can stop the subscription even when the primary journal is poisoned. Cleanup failures remain failures; no sweep, replay or global-absence claim is made. Preserve sensitive state only for the needed reconciliation/evidence period, then remove that run's private captures, configuration, secret and logs; the harness does not delete unresolved evidence automatically.
