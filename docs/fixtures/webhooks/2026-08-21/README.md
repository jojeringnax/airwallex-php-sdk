# Webhook fixture provenance

Read the [webhook catalogue](../../../webhook-contracts.md) for event interpretation, ownership and evidence gaps. These files are sanitized **synthetic documentation fixtures**, authored on 2026-11-08 against API `2026-08-21`; none was captured from an account or signed delivery.

[manifest.json](manifest.json) maps each event fixture group to its official Retrieve reference, API path and response schema, and records the provider specification version/MD5. Each group is a JSON array of complete illustrative event envelopes. Cases are independent observations, not a delivery timeline. [payment-source-retrieve.json](payment-source-retrieve.json) is a resource response, not an event.

## Derivation and limits

- Event names come from the selected API page's `activeCategory.webhookEnvents`; resource fields come from `activeCategory.components.schemas` and its Retrieve endpoint's 200 response reference. All required fields of the selected resource schema are present. Optional fields illustrate only the documented state or linkage; their omission elsewhere is not a nullability claim.
- Envelopes are constructed using the generic [payload reference](https://www.airwallex.com/docs/developer-tools/webhooks/listen-for-webhook-events#webhook-payload): `id`, `name`, applicable owner ID, `created_at`, `version` and `data.object`. Billing examples deliberately use organization ownership from the resource contract. The catalogue records the conflicting product samples; these fixtures do not resolve actual wire shape.
- All IDs, request identifiers and timestamps were invented. No original customer data, credentials, signatures, secrets, payment-card details, fingerprints, client secrets, hosted URLs or account exports were copied. Method details are limited to the type and, for verified card linkage, its placeholder ID. This is a sanitation-by-construction record, not a claim that provider IDs have these formats.
- Invoice monetary fields remain JSON numbers as declared by the API; consumers must preserve exact decimals. Empty discount arrays and disabled tax fields satisfy required response shapes without adding deferred discount/tax capabilities.
- The Consent pending case uses Bacs Direct Debit and the paused case uses PayTo, following status descriptions. The Consent method schema has a `payto` property although its descriptive type list omits it; the explicit PAUSED status description supports this constructed case. Their method variants illustrate Consent states only; they do not establish non-card Billing Source eligibility. The verification-failed case illustrates `REQUIRES_PAYMENT_METHOD`; other returned states require inspection.
- No fixture proves a transition's previous state, exhaustive optional fields, a successful Retrieve request, a signature, delivery ordering or entitlement. The source schema has no status or verified webhook names.

## Re-verification and sandbox replacement

On re-review, fetch each official reference in the manifest and inspect `__NEXT_DATA__.props.pageProps.currentVersion` and the matching `versionItems` specification identifier. Compare the complete selected event-name set, Retrieve path/schema reference, required fields, types, enums and relevant status descriptions. Product pages alone do not pin a schema. Review JSON syntax and every illustrative state/link against the catalogue; do not change the version merely because a URL now defaults to a newer one.

For future sandbox evidence under [#17](https://github.com/jojeringnax/airwallex-php-sdk/issues/17) / [#42](https://github.com/jojeringnax/airwallex-php-sdk/issues/42), configure sandbox explicitly with external credentials. Record event subscription version, resource retrieval version, event name, environment, owner kind, capture method and result. Replace sensitive identifiers consistently across related resources, remove credentials and customer/instrument details, and preserve field spelling, nesting, types and relevant state. Keep original signed bytes and receiver secrets outside version control; a sanitized or reserialized body cannot validate an original signature. Review redaction and provenance before adding evidence. Keep synthetic and captured examples distinguishable.
